## 二、复核明细

### 2.1 sessions 表与 token 存储（通过）

- `sessions(token_hash PK, user_id FK→users, expires_at, created_at)`，`idx_sessions_user` 索引（[lib/db/init.ts](../../sumaitong/lib/db/init.ts#L135-L142)）。
- 会话 token 由 `randomBytes(32).toString('hex')` 生成（64 hex），**数据库只存 `SHA-256(token)`**，原始 token 仅通过 HttpOnly Cookie 下发（[session.ts](../../sumaitong/lib/auth/session.ts#L34-L49)）。
- 过期：读取时 `expires_at <= Date.now()` 即删除该行并返回 null（L89-93）；TTL 7 天（L7）。
- 实测：`sessions.token_hash != token`、`token_hash == sha256(token)`；篡改 cookie 任意一位、未知 token、无 token 全部 401；过期行访问后 401 且行被删除。

### 2.2 Cookie 属性（通过，Secure 依赖部署）

`setSessionCookie` 设置：`HttpOnly: true`、`SameSite: lax`、`Path: /`、`Max-Age = 7d`、`Secure = (NODE_ENV === 'production')`（[session.ts](../../sumaitong/lib/auth/session.ts#L137-L149)）。登录/注册响应均下发；logout 下发同名空值 + `Max-Age=0` 清除。测试逐项断言。

### 2.3 GET /api/auth 与身份返回（通过）

- 无会话 401 `UNAUTHORIZED`；有效会话返回 `{success, role, user:{id,username,email,role,created_at}}`，**不返回 password**。
- 角色每次请求 JOIN `users` 实时读取；实测 admin 将用户改为 operator 后，现有会话立即读到新角色（无需重登）。

### 2.4 logout 契约（结论见第三节）

- 最终代码同时存在两条路径：`POST /api/auth {action:'logout'}`（[app/api/auth/route.ts](../../sumaitong/app/api/auth/route.ts#L73-L78)）与 `POST /api/auth/logout`（[app/api/auth/logout/route.ts](../../sumaitong/app/api/auth/logout/route.ts)）。
- 二者均为：销毁当前会话、清 Cookie、返回 `{success:true}`；独立路由在无会话时也返回 200（幂等）。
- 实测：logout 后 `GET /api/auth`、`GET /api/task-logs`、`GET /api/admin/users` 全部 401；仅销毁当前 token，同用户其他设备会话仍有效。

### 2.5 guards 与身份来源收敛（通过）

- 会话优先；`AUTH_LEGACY_COMPAT=1` 时才接受 `query userId / body.userId / x-user-id` 兜底，默认关闭（[guards.ts](../../sumaitong/lib/auth/guards.ts#L45-L62)）。
- 无会话 + `?userId=admin`、`x-user-id: admin`、body userId → 全部 401（测试验证）。
- 有 viewer 会话时携带 admin 的 query/header 不生效，admin 接口仍 403；viewer 自助提权 `POST /api/users/role` → 403。
- 显式 body.userId 与他人不一致时：`POST /api/agent`、`/api/auth/password`、`/api/shop` 均 403 `FORBIDDEN`。
- **路由审计**：21 个 API 路由中 18 个调用 `requireUser/requireAdmin/requireRole`；未加 guard 的仅 3 个：`/api/auth/shopify/callback`（OAuth state 校验）、`/api/command`、`/api/config/ai`（见第四节）。

### 2.6 admin / 匿名 / 跨用户（通过）

| 接口 | 匿名 | viewer | admin |
| --- | --- | --- | --- |
| `GET /api/admin/users` | 401 | 403 | 200 |
| `GET/POST /api/admin/shops`、`GET /api/admin/stats` | 401 | 403 | 200 |
| `GET /api/users/all` | 401 | 403 | 200 |
| `POST /api/users/role` | 401 | 403 | 200（并即时生效到会话角色） |

跨用户隔离实测：任务列表仅返回会话用户数据；跨用户任务详情 404；`/api/shop` 仅返回本人店铺；`/api/data` 匿名 401、按会话过滤；dashboard/stats 按会话聚合。管理端全局可见属设计预期。

### 2.7 改密吊销其他会话（通过）

`POST /api/auth/password` 身份只取会话（body userId 不一致 → 403），校验当前密码后更新哈希，并调用 `destroyOtherSessionsForUser(user.id, 当前 token)` 保留当前会话（[app/api/auth/password/route.ts](../../sumaitong/app/api/auth/password/route.ts#L92-L95)）。

实测（注册→改密全流程）：改密后其他设备 token → 401；当前 token → 200；该用户 sessions 仅剩 1 条；旧密码登录失败、新密码登录成功；匿名改密 401、错误当前密码 400。

### 2.8 前端身份收敛（通过）

grep `app/ lib/ hooks/ components/`：

- 无 `sessionStorage` 的 userId/userRole；无 `?userId=` 拼接到 API 的调用（仅 API 服务端代码注释/兜底参数）。
- `localStorage` 仅用于 `content-draft` 草稿，不含身份。
- 统一经 `lib/auth/auth-context.tsx` 的 `AuthProvider`：`GET /api/auth` 恢复会话（401 视为未登录），`useAuth()` 提供 user/role/logout；dashboard/admin 布局按服务端 user 判断并跳转；login 页登录/注册成功后 `refresh()`，不再写 sessionStorage。

## 四、发现的问题

1. **未鉴权的 `/api/command`**（中）：`NLCommandParser` 直接解析任意命令；若配置了 `OPENAI_API_KEY`，未登录者可触发 LLM 调用（成本/DoS），虽不泄露用户数据。建议加 `requireUser`。
2. **未鉴权的 `/api/config/ai`**（低）：匿名可读取 `apiKeyConfigured` 与 `modelName`（不泄露 key 本体）。建议加 guard 或降级为服务端内部使用。
3. **注册忽略 email**（低）：前端注册表单提交 `email`，但后端 `register` 固定 `email: null`（`app/api/auth/route.ts`），用户在个人中心看不到邮箱；属前后端契约不一致，非安全问题。
4. **会话清理策略**：仅“访问时惰性删除过期行”，无定时清理任务；sessions 表会随过期未访问记录增长。建议启动时/定时 `DELETE FROM sessions WHERE expires_at < now`。
5. **固定 7 天 TTL、无滑动续期**：用户 7 天后强制重登；长会话体验需权衡（当前无 remember-me）。
6. **Cookie 安全依赖部署**：`Secure` 仅在 `NODE_ENV === 'production'` 时开启；若生产以 HTTP 暴露或反向代理未正确设置 NODE_ENV/HTTPS，Cookie 可能不以 Secure 下发或被丢弃。Cookie 名未使用 `__Host-` 前缀；`GET /api/auth` 未显式设置 `Cache-Control: no-store`（前端虽传 no-store，服务端仍建议显式）。
7. **CSRF 防护不完整**：无 CSRF token/Origin 校验，仅依赖 `SameSite=Lax` + JSON Content-Type。现代浏览器可阻挡跨站 POST，但属纵深防御缺失（配合 XSS 时风险上升）。

## 五、残余风险汇总

| 编号 | 风险 | 说明/建议 |
| --- | --- | --- |
| R1 | CSRF | SameSite=Lax 非完整防护；建议对状态变更接口校验 Origin/Referer，或引入双提交 token |
| R2 | Cookie `Secure` 依赖 HTTPS | 生产必须 HTTPS + `NODE_ENV=production`；否则 Cookie 可能被降级或登录异常 |
| R3 | 会话清理策略 | 惰性删除导致表增长；建议定时任务清理 + 监控 sessions 数量 |
| R4 | `AUTH_LEGACY_COMPAT=1` 过渡开关 | 开启后 query/body/header userId 可伪造身份，**严禁生产开启**；建议增加“非 production 才生效”硬约束或启动日志告警 |
| R5 | `/api/command`、`/api/config/ai` 无鉴权 | 成本暴露/信息暴露（低-中）；建议补 guard |
| R6 | 无 per-user 会话上限/设备管理/logout-all | 被盗 token 只能等过期或改密吊销；建议提供“退出所有设备” |
| R7 | 多实例限流与登出 | 登录限流为进程内 Map；terminate/session 跨实例一致性依赖共享 DB（会话本身已 DB 化，风险低；限流风险同 B-05） |
| R8 | 注册 email 丢失 | 前端提交 email 被后端忽略，影响用户资料完整性 |
| R9 | 无会话续期/记住我 | 7 天固定过期，长周期使用需重新登录 |

## 六、结论

C-02 的验收目标——服务端会话取代客户端 sessionStorage、token 仅存哈希、HttpOnly Cookie、所有身份接口只认会话、admin/匿名/跨用户边界正确、logout 可用、改密吊销其他会话——**全部通过独立测试**（新增 17 例，全量 66/887 绿、tsc 0 error）。

**通过条件**：生产环境强制 HTTPS 且 `NODE_ENV=production`；严禁启用 `AUTH_LEGACY_COMPAT`；建议补齐 CSRF 纵深防御、`/api/command` 与 `/api/config/ai` 鉴权、会话定时清理，并统一 logout 规范入口。
