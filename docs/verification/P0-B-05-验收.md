## 二、逐项验收结论

### 2.1 密码哈希算法（通过）

证据：[lib/auth/password-hash.ts](../../sumaitong/lib/auth/password-hash.ts)

- `hashPassword`（L67-78）使用 `scryptSync`，参数 `N=16384, r=8, p=1`（L3-5），每次调用 `randomBytes(32)` 生成新盐（L68），输出 `scrypt$N$r$p$salt$key`，密钥 64 字节（L6-7、L70-77）。
- 校验使用 `timingSafeEqual`（L109-116、L136），长度不等时先返回 false，避免抛异常。
- **无 SHA-256 生成**：`createHash` 全项目仅出现在 `password-hash.ts:140`，位于旧格式兼容校验分支；`hashPassword` 函数体内无 `sha256`/`createHash`（由新增测试静态断言保证）。
- 盐唯一性：10 次同密码哈希，哈希与盐集合均为 10 个不同值。

### 2.2 明文放行移除（通过）

证据：[lib/db/user-repository.ts](../../sumaitong/lib/db/user-repository.ts#L24-L41)

- `verifyPassword` 已无「数据库字段等于明文也放行」分支（原 `if (user.password === password)` 已删除）；静态断言确认源码无 `password === password` 形态，且仅通过 `verifyPasswordHash` 校验。
- DB 集成用例：以明文 `plaintextPassword` 建行后 `verifyPassword('plaintextPassword')` 返回 `false`（`tests/auth/password-hash.test.ts` 集成段）。
- HTTP 层：改密接口在 DB 存明文时，即使 `currentPassword` 与明文完全一致也返回 `400 INVALID_CREDENTIALS`，且不触发 `update`（新增测试）。

### 2.3 旧 SHA-256 兼容与静默升级（通过）

- `isLegacyHash`（L81-83）识别 64 位 hex，大小写不敏感；`verifyPasswordHash` 对旧哈希计算 SHA-256 后用 `timingSafeEqual` 比较（L139-143）。
- `needsRehash`（L94-107）对旧哈希、损坏值、过期 scrypt 参数返回 true；`UserRepository.verifyPassword` 仅在 `verifyPasswordHash` 返回 true 后才 `hashPassword` + `update`，且包在 `try/catch` 中（更新失败仅 `console.warn`，仍返回 true）→ **升级动作不会导致登录失败**。
- 源码顺序断言（先 verify、后 needsRehash、再 update，update 在 try/catch 内）+ 集成用例（旧行登录成功后变为 `scrypt$` 且再次登录成功）双重验证。

### 2.4 密码策略（通过）

证据：[lib/auth/password-policy.ts](../../sumaitong/lib/auth/password-policy.ts#L13-L37)

- 边界：7 位拒绝（提示 at least 8）、8 位通过、128 位通过、129 位拒绝（提示 at most 128）；空串、纯空白、`undefined/null/数字` 均拒绝。注册（`app/api/auth/route.ts:90`）与改密（`app/api/auth/password/route.ts:39`）均调用该策略，失败返回 `WEAK_PASSWORD` + 400。

### 2.5 登录限流（通过，按接口层验证）

证据：[lib/auth/login-rate-limit.ts](../../sumaitong/lib/auth/login-rate-limit.ts)、[app/api/auth/route.ts](../../sumaitong/app/api/auth/route.ts#L110-L135)

- 键为 `username.toLowerCase()|clientIp`（L119-122），IP 取 `x-forwarded-for` 首项 → `x-real-ip` → `unknown`（L105-116）。
- 连续 5 次失败后第 6 次返回 **429 + `Retry-After`**（L112-121）；第 5 次本身仍返回 `INVALID_CREDENTIALS`（200 语义），第 6 次起拒绝。
- 成功登录调用 `clearLoginFailures`（L132），随后可再失败 4 次不被限流（新增测试验证）。
- 窗口 60s、阈值 5 次（L1-2），窗口过期后自动放行（已有测试）。

### 2.6 改密前端接线（通过，页面级无自动化测试）

证据：[app/dashboard/profile/page.tsx](../../sumaitong/app/dashboard/profile/page.tsx#L113-L216)、[app/login/page.tsx](../../sumaitong/app/login/page.tsx#L152)

- 个人中心改密弹窗已改为 `fetch('/api/auth/password')`，提交前本地校验：必填、8-128 位、两次一致、新旧不同；按 `code` 映射 `WEAK_PASSWORD / INVALID_CREDENTIALS / SAME_PASSWORD / RATE_LIMITED` 与兜底提示，成功后清空表单并提示。
- 注册页最小长度同步为 8-128（`app/login/page.tsx:152`）。
- 说明：`profile/page.tsx` 处理了 429/`RATE_LIMITED` 分支，但改密接口当前**未接入限流**，该分支实际不可达（见残余风险 R4）。页面级行为无 jest 用例覆盖（`tests/components` 无 profile 测试），本轮仅做源码复核。

## 三、残余风险

| 编号 | 风险 | 影响 | 依赖/建议 |
| --- | --- | --- | --- |
| R1 | 改密后不失效任何会话 | 旧登录态在改密后仍可继续使用；不满足"改密即踢出" | 依赖 **P0-B-04**（服务端会话/Cookie 尚未建立）；B-04 完成后需补充改密触发会话吊销 |
| R2 | 改密接口 `userId` 仍由请求 body 传入（`app/api/auth/password/route.ts:24,60`） | 任意调用方可携带他人 `userId` + 已知当前密码改他人密码（IDOR） | 依赖 **P0-C-02**（身份改由服务端会话解析）；当前无会话，属已知残留 |
| R3 | 限流键依赖 `x-forwarded-for` / `x-real-ip`，两者均可由客户端伪造 | 攻击者每次换 IP 头即可绕过 5 次阈值 | 仅在受信反向代理后可信；建议由网关写入并剥离客户端同名头 |
| R4 | 改密接口无限流，且只校验当前密码 | 已知 `userId` 时可暴力猜测当前密码（每次 scrypt ~50ms，仍可被并行放大） | 建议复用 `login-rate-limit` 为改密单独建键（按 userId+IP） |
| R5 | 限流状态为进程内 `Map` | 多实例/重启后阈值失效；Serverless 横向扩容下形同虚设 | 多实例部署需外置 Redis/DB 计数 |
| R6 | 旧 SHA-256 兼容期内仍接受弱哈希 | 升级前泄漏的旧哈希可用彩虹表破解，撞库仍可能成功 | 属迁移窗口的合规折中；建议对长期未登录账号强制重置或后台批量迁移 |
| R7 | 密码策略仅长度（8-128） | 允许 `12345678`、常见弱口令；无口令字典/复杂度/泄露库校验 | 可后续加 zxcvbn 或常见口令黑名单（非 P0 阻塞） |
| R8 | 用户名枚举（低危） | 用户不存在与密码错误的响应耗时不同（少一次 scrypt 派生）；错误文案相同但时序可区分 | 若需抗枚举，可对不存在用户做一次假 scrypt 派生 |
| R9 | 升级失败仅 `console.warn`，无监控指标 | 大量旧哈希长期不升级且无告警 | 建议记录结构化日志/计数 |
