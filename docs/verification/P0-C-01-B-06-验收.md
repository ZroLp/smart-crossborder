## 二、C-01 验收明细

### 2.1 taskId / displayId 契约（通过）

- `POST /api/agent` 返回 `data.taskId`（数字字符串）与 `data.displayId`（`TSK-YYYYMMDD##`），并带 `status`、`result`（[app/api/agent/route.ts](../../sumaitong/app/api/agent/route.ts#L56-L81)）。
- 同一任务双标识可互查：`findTask` 支持数字 id 与 displayId；列表、详情、progress 的 taskId/displayId 一致（新增测试逐项断言）。
- `formatDisplayId` 使用 `created_at` 日期 + 至少 2 位 id（[task-service.ts](../../sumaitong/lib/agents/task-service.ts#L56-L60)），同日多任务不重复。
- 详情接口同时返回 `id=displayId`、`task_id=数字 id`、`db_id`（[task-logs/[id]/route.ts](../../sumaitong/app/api/task-logs/[id]/route.ts#L27-L44)）。

### 2.2 状态机（通过）

`TaskStatus` 已含 `paused/terminated`；迁移表：`pending→running`、`running→{paused,terminated,completed,failed}`、`paused→{running,terminated}`、`failed→pending`、`completed/terminated` 终态；`isTerminal` 含 terminated（[task-state-machine.ts](../../sumaitong/lib/framework/task-state-machine.ts#L4-L26)）。非法迁移抛 `InvalidTaskStateError`，路由映射 409。

### 2.3 任务生命周期落库（通过）

- 创建即写 `task_logs`（pending，含 user_id/input）；执行前更新 running；成功写 output、失败写 error，终态 completed/failed/terminated。
- 实测：真实 customer-service 执行 → 行 status=completed、output.intent=shipping；失败执行（selection 空输入）→ status=failed、error 非空；terminated 由控制接口写入。
- 交叉校验：POST 响应的 taskId/status 与 `task_logs` 行完全一致。

### 2.4 五步进度（通过，但语义近似合成）

- 执行开始写 `agent_progress`（5 步 pending），成功后 `completeRemainingSteps` 一次性把 5 步全部置 completed（[task-service.ts](../../sumaitong/lib/agents/task-service.ts#L164-L176)）；失败仅首步 failed、其余 pending。
- `GET /api/agent/progress` 返回 `taskStatus/status/displayId/steps[5]`；跨用户 404；未知 404。
- 注意：进度由 task-service 合成，Agent 内部未调用 `trackProgress/updateStep`，因此 duration 不代表真实阶段耗时（见风险 R3）。

### 2.5 控制接口（通过）

| 接口 | 200 | 409 | 404 | 400 |
| --- | --- | --- | --- | --- |
| pause | running→paused | pending/completed/failed/terminated | 未知任务 | 无 taskId / 非法 JSON |
| terminate | running→terminated、paused→terminated | pending/completed/failed | 未知任务 | 同上 |
| retry | completed/failed/paused/terminated → 新 taskId + completed | pending/running | 未知任务 | 同上 |

- retry：新任务复用原 input、保留 user_id；旧任务状态不变（实测 failed 保持 failed、terminated 保持 terminated）。
- 鉴权：匿名 401、跨用户统一 404（不泄露存在性）。

### 2.6 任务日志列表/详情（通过）

- `/api/task-logs` 支持分页、agentType/status 过滤、按 `user_id` 隔离、按 id 倒序；无 task 的用户返回空列表。
- legacy `user_id=NULL` 的历史任务不会出现在任何用户列表（`findByUserId` 严格等值）。
- 详情：数字 id 与 displayId 均可解析；含 steps（5 步）与 output/error。

## 三、B-06 验收明细

### 3.1 seed 幂等（通过）

- 每个用户 1 店铺 + 3 商品 + 3 订单；已有店铺复用不重建；products/orders 任一非空则整体跳过；无用户空操作；事务包裹（[lib/db/seed.ts](../../sumaitong/lib/db/seed.ts)）。
- 实测：首次 `seeded=true`（2 用户 → 2 店/6 商品/6 订单），第二次 `seeded=false` 且计数不变；预置店铺时 shops 只建缺失的 1 个。

### 3.2 数据页与用户隔离（通过）

- seed 后 `/api/dashboard/stats` 返回 hasData=true、orders=3、revenue=238.70；`/api/data?type=products` 各用户只看到自己的 3 条，shop_id 集合不相交。
- 仪表盘聚合按当前会话用户的店铺计算（[app/api/dashboard/stats/route.ts](../../sumaitong/app/api/dashboard/stats/route.ts)）。

### 3.3 Shopify 同步（通过）

- OAuth 回调完成 token 交换、建/更新 shop 后调用 `syncShopifyData` 拉取 shop/products/orders；同步失败不阻断授权（200 + success）。
- 商品按 name、订单按 order_number 去重，二次同步新增 0；远端失败收集 `errors` 不抛异常（[lib/shopify/sync.ts](../../sumaitong/lib/shopify/sync.ts)）。

## 四、发现的问题（按严重度）

### P1（阻断演示闭环）：5/6 业务页真实载荷执行失败

用前端页面实际提交的载荷逐个调用 `POST /api/agent`（真实 Orchestrator），实测：

| 页面 | 提交载荷 | 结果 | 直接原因 |
| --- | --- | --- | --- |
| 选品 | `{category, region, keyword}` | **failed** `Invalid input for agent: selection` | Agent 要求 `products[]`，页面无该字段 |
| 建站 | `{action:'create'}` | **failed** `Invalid input for agent: store-builder` | 要求 `selectedProducts[]` |
| 内容 | `{language, productId}` | **failed** `Invalid input for agent: content` | 要求 `products[]` |
| 投流 | `{adData:{campaigns}}` | **failed** `Invalid input for agent: fulfillment` | ad-optimizer 通过校验后自动链到 fulfillment，`nextAgentInput` 无 `order` |
| 履约 | `{action:'sync'}` | **failed** `Invalid input for agent: fulfillment` | 要求 `order` 对象 |
| 客服 | `{message, language}` | **completed** | 输入契约匹配 |

影响：C-01 的「taskId/进度/暂停/重试闭环」在 API 层成立，但**用户真实操作只有客服页能跑到 completed**，其余任务落到 failed 且进度首步失败。seed 数据（products）也未被选品页用于构造 `products[]` 入参。

### P2：`chain` 语义重复且易误导

`Orchestrator.executeTask` 在结果带 `nextAgent` 时**无论 chain 是否为 false 都会继续串链**（[orchestrator.ts](../../sumaitong/lib/framework/orchestrator.ts#L34-L39)）；`chain:true` 只是改走 `executeChain`。前端页面均未传 `chain`，因此普通「选品」请求实际会串到建站/内容/投流并在 ad-optimizer→fulfillment 处失败。建议统一为：单 Agent 请求不自动串链，或修正 `nextAgentInput` 契约。

### P3：五步进度为合成数据

Agent 未调用 `trackProgress/updateStep`（全项目 grep 无调用），进度由 task-service 一次性标记 completed；注入的 `progressTracker` 实际未被 Agent 使用（仅 customer-service 使用 sharedContext）。duration/步骤状态不反映真实执行阶段。

### P4：pause 无 resume 路径

状态机允许 `paused→running`，但无 resume 路由、前端 `useAgentTask` 把 paused 视为终态并停止轮询，只能 retry 生成新任务；paused 旧任务永久停留。

### P5：terminate 不真正中断 LLM

`terminateTask` 只 abort 本地 AbortController 让 `Promise.race` 提前返回（[task-service.ts](../../sumaitong/lib/agents/task-service.ts#L302-L318)）；`callOpenAI` 的 fetch 未绑定该 signal（仅自身 timeout），在途请求继续消耗 token。

### P6：同步执行 + 无队列，pause/terminate 难命中

POST /api/agent 同步等待执行完成（链式最长 6×30s LLM 超时）；真实 UI 上 running 窗口极短，暂停/终止大概率遇到已完成返回 409，前端轮询也只能看到终态。验收是通过直接构造 running 状态验证接口的，真实链路未覆盖并发暂停。

### P7：displayId 查询依赖 1000 行扫描

`findTask` 按 displayId 查找时 `findAll(1000,0)` 线性扫描（[task-service.ts](../../sumaitong/lib/agents/task-service.ts#L91-L100)），任务超 1000 条后旧任务 displayId 查不到（404）；`created_at` 异常时日期段用当天，跨天可能改变 displayId。

### P8：B-06 数据来源仍有限

- Agent 执行结果只写 `task_logs`，不写 `products/orders/shops`；选品结果不会进入商品表，数据中心/仪表盘依赖 seed 与 Shopify 数据。
- seed 仅在 `SEED_DEMO_DATA=true` 时由 `initDatabase` 触发（[init.ts](../../sumaitong/lib/db/init.ts#L163-L171)）；该变量未写入 `.env.example`/README，默认关闭时首启仍为空库。
- README 仍写「选品、投流、合规、任务日志等页面以演示数据为主」（文档漂移）。

### P9：Shopify 同步细节风险

- 商品仅按 name 去重：同名商品的价格/库存/状态不会更新。
- `orders.order_number` 全局 UNIQUE：跨店铺同订单号会触发约束异常，被同步的宽 catch 收集为 error，该店铺本批后续订单不导入。
- 同步为串行 3 次请求，无分页（limit=50），无增量游标。

### P10：userId 过渡方案

后端 `guards.ts` 已改为会话优先，`AUTH_LEGACY_COMPAT=1` 时允许 query/body/x-user-id 兜底（[guards.ts](../../sumaitong/lib/auth/guards.ts#L40-L62)）；该开关若在生产开启则身份可伪造。C-02 前端正在改造，前后端切换期间存在混用窗口（会话缺失时页面调用会 401）。

## 五、残余风险汇总（lead 指定项）

1. **同步执行导致 pause/terminate 难触发**（P6）：真实运行窗口短，暂停/终止+重试链路只在构造状态下验证。
2. **terminate 未真正中断 LLM**（P5）：本地 race 返回，远端请求继续，成本不可控。
3. **userId 过渡方案**（P10）：legacy compat 开关可伪造身份；前端仍处改造期，会话缺失/401 处理需联调。
4. 进程内 `abortControllers` Map：多实例部署时 terminate 无法命中其他进程的任务。
5. 进度合成为主（P3），不能作为耗时/阶段质量指标。
6. displayId 扫描上限 1000（P7）；任务量增长后需索引/独立 display_id 列。
7. 旧库 `task_logs.user_id=NULL` 数据永久不可见，需迁移脚本或管理员视图。
8. seed 默认关闭且未文档化（P8），演示环境需显式开启。

## 六、结论

- **C-01**：taskId/displayId 契约、状态机（含 paused/terminated）、生命周期落库、五步进度、三控制接口、列表/详情、用户隔离全部通过独立测试（20/20），全量 839 用例与 tsc 全绿。
- **C-01 业务闭环未通过**：真实页面载荷下仅客服页可执行成功，其余 5 个业务入口因「前端 payload ↔ Agent.validate/nextAgentInput」契约不匹配落入 failed；`chain` 语义重复放大该问题。建议作为 P0 级后续修复项（不在本次验收改动范围内）。
- **B-06**：seed 幂等、Shopify 同步去重、用户级数据隔离、仪表盘/数据接口真实化均通过；但 Agent 结果不落业务表、seed 默认关闭，需明确演示环境启用方式与后续落库范围。
